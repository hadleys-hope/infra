# Hadley's Hope: системный дизайн на 5000 домов

Цель: 5000 домов, каждый управляется своей программой на Hope в своей ВМ, всё на одном домашнем сервере (Intel N100, 4 ядра, 16 ГБ). Вертикально масштабироваться нельзя, горизонтально нежелательно. Ничего не должно падать или зависать, сайт должен оставаться отзывчивым.

Все цифры ниже либо измерены (помечено **изм.**), либо выведены из измеренных по формуле. Измерения сделаны на одном общем ядре облачной песочницы: на N100 ядер четыре, поэтому запас там больше.

## Обозначения

| Символ | Смысл | Значение |
|---|---|---|
| $N$ | число домов (ВМ) | 5000 |
| $v$ | тиков симуляции в секунду (скорость 20 = 20 тиков/с) | 20 |
| $T$ | период опроса дома в тиках: дом шлёт показания раз в $T$ тиков | 10 (можно 20) |
| $S$ | число секторов | 6 |
| $M$ | число подписчиков на всё (`hh/#`), например мониторинг | 1 |
| $V$ | число зрителей сайта одновременно | 5–20 |

## 1. Потоки на шине

Показания домов (мир → ВМ) и ответы (ВМ → мир):

$$R = \frac{N \cdot v}{T} = \frac{5000 \cdot 20}{10} = 10\,000 \text{ показаний/с}$$

На каждое показание один ответ, всего публикаций в брокер $2R = 20\,000$/с. Брокер доставляет каждое сообщение каждому подписчику:

$$D = R \cdot (1 + M) + R \cdot (1 + M) = 2R\,(1+M) = 40\,000 \text{ доставок/с при } M = 1$$

| Топик | Кто пишет | Кто читает | Сообщений/с |
|---|---|---|---|
| `hh/house/{id}/sensors` | world | hope-runtime, мониторинг | $R$ = 10 000 |
| `hh/house/{id}/actuators` | hope-runtime | world, мониторинг | $R$ = 10 000 |
| `hh/env/weather`, `hh/env/power`, `hh/tick` | world | все | $3v$ = 60 |
| `hh/house/{id}/log` | hope-runtime | мониторинг | редко, только `log()` и сбои |
| `hh/runtime/status` | hope-runtime | мониторинг | 0,5 |

**Изм.** (`bus-bench` + Mosquitto + `hope-runtime`, 5000 домов, $v = 20$, $T = 10$, $M = 1$): 10 060 показаний/с, 10 060 ответов/с, 20 120/с мониторингу, ответили все, задержка p50 17 мс, p99 48 мс. Mosquitto занял **16 %** ядра, runtime **12 %**.

Потолок на одном общем ядре (генератор, брокер и runtime делят его): $T = 1$, то есть 39 600 сообщений/с в каждую сторону, все с ответом, p99 460 мс, ядро загружено полностью.

Вывод: **MQTT справляется с 5000 домов с запасом примерно в 4–6 раз** даже на одном ядре. Mosquitto однопоточный, поэтому при росте до сотен тысяч сообщений/с его заменяют на многопоточный брокер (EMQX, NanoMQ) без изменения кода, протокол тот же.

## 2. Виртуальные машины

**Изм.** (`hope-runtime --bench`, 5 программ домов на Hope, 1 поток):

| | 300 домов | 5000 домов |
|---|---|---|
| создание всех ВМ | 1,6 мс | 27 мс |
| память на дом | 6,9 КБ | 6,7 КБ (53 МБ на все) |
| обработка показания (обработчик + разбор JSON + ответ) | p50 3,3 мкс | p50 4,1 мкс, p99 34 мкс |
| пропускная способность одного потока | 129 000/с | 117 000/с |

Нагрузка на процессор от ВМ:

$$C_{vm} = \frac{R}{P_{rt}} = \frac{10\,000}{117\,000} \approx 0{,}09 \text{ ядра}$$

где $P_{rt}$ это показаний в секунду на один поток runtime. Запас **примерно в 11 раз на одном потоке**, а потоков на N100 можно дать 2–3.

Программа, ушедшая в бесконечный цикл, не роняет остальных: **изм.** 500 из 1000 домов с `while true`, каждый дал 3 сбоя по бюджету шагов и ушёл в карантин на 600 тиков, остальные 500 ответили на все показания.

Чистый интерпретатор: **изм.** около $8 \cdot 10^7$ инструкций/с на ядро. Программа дома укладывается в сотню инструкций плюс вызовы `sense`/`act`, поэтому основное время уходит не на байткод, а на хеш-таблицы и строки вызовов хоста (см. п. 6).

## 3. Компиляция

**Изм.** холодный запуск компилятора (JVM) на файл 0,31–0,48 с. Компилируются программы, а не дома: 5 программ за ~2 с, и это делается один раз при сборке образа, а не при старте.

## 5. Сайт

**Изм.** на 5040 домах: `/state` 891 КБ (из них 516 КБ поэлементная гидравлика), сжатый Caddy 63 КБ, сборка 30 мс под блокировкой мира. Благодаря кэшу на тик собирается не чаще раза за тик на всех зрителей, но 30 мс под блокировкой за каждую сборку отнимают время у тика, а 63 КБ × 3,3 опроса в секунду это ~210 КБ/с на зрителя.

Решение: WebSocket вместо опроса, бинарный кадр вместо JSON, только изменившиеся дома:
- полный кадр: на дом ~8 байт (температура int16, флаги, мощность), $5000 \cdot 8 = 40$ КБ, отправляется при подключении;
- дельта: дома, у которых что-то изменилось с прошлого кадра, при 5 кадрах/с обычно единицы КБ;
- кадр собирается один раз за тик на всех зрителей (как уже сделано для `/state`), так что $V$ не влияет на нагрузку мира.

Загрузка страницы уже исправлена (патчи world-0001..0003): всё нужное приходит за 0,36 с вместо 2,1 с, первый `/state` за 0,8 с вместо 6.

## 6. Устойчивость: что уже есть и что добавить

| Отказ | Что происходит |
|---|---|
| программа дома зациклилась или упала | бюджет шагов останавливает обработчик, ВМ пересоздаётся; 3 сбоя подряд, и дом в карантине на 600 тиков (**реализовано**) |
| runtime не успевает | для каждого дома хранится только последнее показание, устаревшие отбрасываются, очередь не растёт (**реализовано**) |
| runtime упал | мир через 15 тиков без команд переводит дом на встроенный термостат (**есть в world**); Docker перезапускает контейнер |
| брокер перезапустился | runtime переподключается с паузой до 5 с и переподписывается (**реализовано**) |
| мир упал | Docker перезапускает, мир восстанавливается из `world.pkl` (**есть**) |
| сайт: много зрителей | один снимок на тик для всех (**реализовано для `/state`**), дельты по WebSocket (**предстоит**) |

Что добавить: healthcheck в compose для runtime по `hh/runtime/status`, лимиты CPU и памяти на контейнеры, чтобы ни один сервис не мог отнять ресурсы у остальных.

## 7. Если всё-таки не хватит

По порядку, от дешёвого к дорогому:
1. Увеличить $T$ до 20: всё на шине и в ВМ делится пополам.
2. Пакеты на сектор (п. 4).
3. Несколько процессов runtime по диапазонам домов (`--houses` + сдвиг id), шина та же. Это горизонтальное масштабирование без смены архитектуры, хоть на одной машине, хоть на двух.
4. Многопоточный брокер (EMQX/NanoMQ) вместо Mosquitto.
5. Ускорить ВМ: интернированные имена вместо строк в вызовах хоста, `Value` без `std::string` внутри, без аллокаций стека на вызов.

## 8. Распределение ядер N100 (оценка)

| Сервис | Ядер |
|---|---|
| world (Python, физика, финансы, HTTP): тик ~11–16 мс × 20 тиков/с | 0,3–0,4 |
| hope-runtime (5000 ВМ, 2 потока) | 0,1–0,3 |
| Mosquitto | 0,1–0,2 |
| Caddy, мониторинг, ОС | 0,5 |
| **запас** | **~1,5–2** |

Тик мира на 5040 домах измерен (п. 4); на N100 одно ядро может быть медленнее ядра песочницы, поэтому запас считаем с коэффициентом 2.
